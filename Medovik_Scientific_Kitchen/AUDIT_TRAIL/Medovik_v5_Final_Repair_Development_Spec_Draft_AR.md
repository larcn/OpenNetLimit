# Medovik v5
## وثيقة الإصلاح والتطوير النهائية — مسودة التنفيذ المعتمدة على التدقيق

**الحالة:** جاهزة للتنفيذ بعد المراجعة  
**المرجعية:** تقارير المراحل 1 و2A و2B و2C وتقرير المرحلة 3 وسجل المشكلات.

---

# 1. هدف الإصدار

إنتاج نسخة نهائية من Medovik تحتفظ بكل وظائف v5، لكنها:

- لا تغيّر وصفة مصدرية صامتًا.
- تميز الحقيقة المرجعية عن القيمة الهندسية والتقدير.
- تفصل السمك الخام عن المخبوز.
- تحلل الحلاوة والتركيب دون Brix زائف أو سكر مفقود.
- تقدم بروتوكولًا مطابقًا لعائلة العملية.
- تحفظ ما يراه المستخدم فعلًا.
- تقبل المدخلات القديمة عبر migration واضح.
- تجتاز اختبارات حسابية ووظيفية وأمنية.

---

# 2. سياسة الأدلة والقيم

كل قيمة عددية أو توصية تحمل واحدة من الحالات:

- `SOURCE_VALUE`: واردة في الوصفة/المصدر.
- `REFERENCE_RELATION`: علاقة علمية قابلة للنقل ضمن مجالها.
- `ENGINEERING_DEFAULT`: افتراض عملي يعمل تلقائيًا.
- `EMPIRICAL_PRESET`: قيمة خاصة بمدرسة أو preset.
- `USER_MEASURED`: قيمة أدخلها المستخدم.
- `MODEL_ESTIMATE`: ناتج نموذج مع نطاق وثقة.
- `UNKNOWN`: لا توجد معلومة كافية؛ لا يُخترع رقم.

لا تعطل القيم الهندسية التشغيل؛ لكنها لا تظهر كقوانين عالمية.

# 3. تقسيم التنفيذ إلى أربع حزم

## الحزمة A — الحقيقة التركيبية ومخطط البيانات

### A1. Ingredient schema

- فرض الكسور بين 0 و1.
- منع مجموع أكبر من 1 ضمن tolerance.
- فصل `totalSugarFrac` عن `sugarProfile`.
- fallback للسكر غير المفصل دون جمع مزدوج.
- ملفات شوكولاتة قابلة لاختيار النوع: real couverture / compound / unknown، ونسبة الكاكاو أو سكر الملصق.
- نموذج خاص للساور كريم المصفى بدل ضرب كل المكونات في yield واحد.
- coverage report لكل صيغة.

### A2. Formula lineage

إضافة:

- `sourceRecipeId`
- `sourceProcessFamily`
- `sourceFillingId`
- `transformationHistory`
- `massBasis`

وتوحيد التحويلات في `Formula.withItems()`.

### A3. Session schema

- `schemaVersion`.
- migrations متسلسلة.
- ترحيل `doughThicknessMm` القديم مع وسم `legacyAmbiguousThickness` بدل التخمين الصامت.
- تحقق مركزي للـProductSpec.

**اختبارات الحزمة:** composition, mass balance, snapshot/restore, migration.

---

## الحزمة B — المحركات العلمية والهندسية

### B1. عائلات العجين

إضافة process families، على الأقل:

- `HOT_BASE_EGG_ADDED_AFTER_HEAT`
- `EGG_HEATED_FROM_START`
- `BAIN_MARIE_EGG_SYSTEM`
- `SOUR_CREAM_SODA_SPARTAK`
- `ROLLED_WARM`
- `ROLLED_CHILLED`
- `ROLLED_DIRECT`
- `SPREAD_BATTER_SHEET`
- `SOURCE_INCOMPLETE`

كل وصفة تحمل عائلة تحضير وعائلة تشكيل مستقلتين.

### B2. التمبرنج

- اتجاه الدمج input إلزامي.
- لا حكم “آمن” قطعي.
- عرض حرارة الاتزان الحجمية لكل دفعة وحدود النموذج.
- عدم إظهار الأداة للوصفات التي لا تستخدم التمبرنج.
- إزالة hard-coded 20/85/4 من الـRunbook.

### B3. هندسة الطبقات

- فصل السمك الخام/المخبوز.
- التحجيم الحجمي يعتمد السمك المخبوز المستهدف أو preset المدرسة.
- تعليمات الفرد تعتمد السمك الخام.
- سبارتاك يستخدم surface load/spread thickness لا وزن كرات.
- كثافة/عائد الخبز ذات status ونطاق.

### B4. الحلاوة

- إصلاح ملفات السكريات.
- إعادة تسمية Brix الحشو.
- سياسات مستقلة للعجين وعائلات الحشو.
- إظهار requested vs achieved والتغيرات التركيبية.
- عدم ادعاء حفظ البنية بمجرد ثبات solids/water.

### B5. الحشوات

- density source model صريح.
- suitability للداخل/الوجه/الجوانب.
- yield transformation حقيقي للتصفية.
- `Preset Consistency Audit` بدل confidence العلمي الدائري.

**اختبارات الحزمة:** golden recipes, scaling invariants, sweetness families, density/yield states.

## الحزمة C — البروتوكولات والواجهة والحفظ

### C1. بروتوكولات المصدر

- إعادة تحرير الوصفات التسع دون تغيير مقاديرها.
- إصلاح شوقي ويونس.
- حفظ تعليمات الراحة والفرد المصدرية.
- flourPolicy لكل وصفة.
- فصل source text عن editorial guidance.

### C2. الحشوات

- المصدر أولًا.
- عائلة العملية ثانيًا.
- القواعد العامة ثالثًا.
- كشف أي تعارض بدل دمج صامت.

### C3. الواجهة

إضافة/تصحيح:

- شاشة التجميع والنضج أو دمج واضح لا يضيع الـRunbook.
- مصطلحات السمك الجديدة.
- حالات القيمة ومصدرها.
- “غير متاح” بدل 0.
- نطاقات بدل دقة زائفة.
- اختيار حفظ الصيغة الأساسية أو variant أو الدفعة.
- تنبيه عند تجاوز مرحلة غير مكتملة بدل منع إجباري إن كان التنقل الحر مقصودًا.

### C4. الأمن

- لا user text داخل innerHTML.
- escape مركزي للبيانات الديناميكية.
- CSP متوافق مع العمل offline بعد فصل inline handlers إن لزم.
- إشعار نجاح/فشل الحفظ المحلي.

**اختبارات الحزمة:** E2E لجميع المراحل، XSS regression، save/reopen، source fidelity snapshots.

## الحزمة D — الاختبارات والإغلاق

### D1. Unit tests

- Ingredient validator.
- Formula mass/sweetness/coverage.
- Geometry and scaling.
- Dough process families.
- Tempering both directions.
- Filling yield and density states.
- Session migrations.

### D2. Golden fixtures

للوصفات التسع والحشوات التسع:

- المقادير الأصلية.
- نسب الخباز/الكتلة.
- عملية المصدر.
- حرارة وزمن الخبز المصدرية.
- مخرجات التحجيم القياسية.

### D3. Browser tests

- إنشاء وصفة مخصصة وحفظها.
- تعديل حلاوة وحفظ variant.
- تبديل الوصفات والحشوات.
- التنقل إلى التجميع.
- تسجيل الملاحظات دون تنفيذ HTML.
- فتح جلسة قديمة بعد migration.
- طباعة/مقارنة/استعادة.

### D4. بوابة الإغلاق

لا يصدر Final إلا عند:

- صفر BLOCKER مفتوح.
- كل اختبارات الحساب والـE2E ناجحة.
- لا Console/Page errors.
- Functional parity مكتوب ومختبر.
- تقرير تغييرات، تقرير اختبارات، manifest hashes، وحزمة نظيفة.

# 4. ما يُحفظ دون حذف

- الوصفات التسع والحشوات التسع.
- التحجيم حسب الهندسة.
- أوضاع الحجم/وزن الكرة/وزن الدقيق، مع تقييدها حسب العائلة.
- محررات العجين والحشو.
- مكتبة الوصفات والمقارنة.
- التحكم في الحلاوة.
- الحفظ والجلسات والملاحظات والمراجعات.
- مكتبة العلم واستكشاف الأعطال.
- العمل Offline وHTML/CSS/JS الحالي؛ لا انتقال لإطار جديد.

---

# 5. ما يُلغى أو يتغير

- إلغاء اسم Brix للحشوات المركبة.
- إلغاء الحكم القطعي على “تفعيل” الصودا.
- إلغاء بروتوكول تمبرنج عام لكل الوصفات.
- إلغاء استخدام سمك واحد للخام والمخبوز.
- إلغاء الثقة العلمية الناتجة عن مقارنة preset بنفسه.
- إلغاء الدقة العشرية الزائدة للتقديرات.
- إلغاء إضافة قواعد حشو عامة تناقض المصدر.
- إلغاء حفظ صيغة غير التي يراها المستخدم دون اختيار.
- إلغاء HTML غير المهرب للبيانات الحرة.

---

# 6. معايير التطابق الوظيفي

أي وظيفة موجودة حاليًا تعتبر محفوظة ما لم تذكر صراحة في قائمة الإلغاء أعلاه. سيبنى جدول parity قبل التعديل، ويشمل:

- الوظيفة الحالية.
- مكانها.
- شكلها بعد الإصلاح.
- اختبار القبول.
- حالة ترحيل البيانات.
